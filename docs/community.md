# Blur Community：构想摘要

> 状态：P0 与 P1 已实现。P1 的实现取舍与下面的构想有几处不同，见文末「P1 实现记录」，冲突时以那一节为准。
> 前身是 [第一轮朋友实验](community-direction.md) 的话题讨论方案，该方案已主动放弃，原因见第一节。

## 一句话

**社区不是让人互相说话，而是让人看见自己在人群中的位置。**

## 一、我们明确不做的事

- 不做信息流、不做发帖、不做评论区
- 不做关注、粉丝、私信、@
- 不做点赞数、热榜、连续签到
- 不把用户生成的内容当作社区燃料

这不是克制，是算术：**任何一条 UGC 通道都会带来审核义务**。团队没有审核人力，也不应该在比赛周期里背这个包袱。第一轮方案（共同问题 + 接一句）正是卡在这里——它需要一个每天都在场的人，而这个人不存在。

## 二、那社区是什么

它不是一个空间，而是一个**分布**。

| 层 | 内容 | 状态 |
| --- | --- | --- |
| L0 | 一个人的测试结果 | 已上线 |
| L1 | 两个人之间的对比 | 已上线 |
| L2 | 所有人构成的一片场 | 待建（点云） |

L1 已经证明了这件事成立：两个人把画像放在一起，会自然产生"原来你是这样"的对话。L2 只是把"和一个人比"扩展成"看看我在所有人里的位置"。

**社区的价值不在互动，在参照。**

## 三、点云

机制：

1. 每份被主动设为公开的画像，取它的 10 维向量
2. 投影到二维（或三维）空间，成为场上的一个点
3. 点与点之间的距离，就是画像之间的相似度
4. 自己那个点高亮，其余点模糊、无标签

视觉上它应该像一片星尘，而不是一张散点图。这正好接上产品已有的光学场、水彩和模糊语言——**Blur 的社区看起来就应该是模糊的**。

交互边界（P1 只做这些）：

- 只读，不能点开任何一个点
- 不显示排名、不显示百分位、不显示"你超过了多少人"
- 不显示点的身份，即使你们是好友
- 自己的位置可以看，别人的位置只能感知密度

## 四、为什么这个设计成立

**1. 内容由引擎生成，不由用户生产。**
用户能输入的只有昵称和简介，两者都有长度上限。审核面从"无限文本"缩到"两个短字段"，这是数量级的差别。

**2. 匿名身份让"人肉"失去动机。**
系统里没有邮箱、没有手机号、没有 IP。即使有人想追究"那个点是谁"，也没有入口。

**3. 聚合优先，个体最小化。**
后台能看到人群的形状，看不到面具后面的人。这不是技术限制，是产品承诺。

**4. 分享即 opt-in。**
一个点出现，前提是本人主动把画像设为可见。默认不曝光，参与是选择的结果。

## 五、治理：现在不需要管理员，只需要一个开关

没有 UGC，就不需要 moderator。争议的对象不存在——没有人能发一段话让别人不舒服。

需要保留的最小能力，只有三件：

1. 昵称与简介的过滤（词表 + 长度）
2. 单条画像的下架能力（不是删账号）
3. 一个举报入口的占位，哪怕只是收件箱

开发者后台与社区管理员是两件事，将来若真的需要，也必须分开：

| | 开发者后台 | 社区管理员 |
| --- | --- | --- |
| 权力来源 | 系统所有权 | 社区规则授权 |
| 看什么 | 聚合指标 | 被举报的那一条 |
| 做什么 | 发布、迁移、修故障 | 下架、警告 |
| 失败模式 | 隐私越界 | 滥权 |

后台令牌独立于用户身份，数据库只存哈希，不设 `is_admin` 字段。这样即使某天交出审核权，交出去的也是"队列"，不是数据库。

## 六、度量：两个数字，两种口径

- **完成测试**：匿名计数，覆盖所有访客，包括从没注册的人
- **注册身份**：只有用过云端功能才产生，必然小于真实参与人数

两者永远不合并成一个"用户数"。后台只读、只聚合，规模数字走 5 分钟物化快照。

在答辩时，能解释清楚这两个数的差别，比数字本身更大。

## 七、风险，诚实列出

1. **点云会被读成排名。** 只要有位置，就有人问"我在前面还是后面"。文案与视觉必须持续否认优劣，只谈"位置"不谈"高低"。
2. **人少的时候像空房间。** 不造假数据、不显示虚构在线人数。空状态用"你是第 N 个点"承接，把稀少说成早期，而不是失败。
3. **小样本下匿名会被反推。** 朋友之间本来就互相知道彼此的结果，点云一旦显示身份就等于公开。所以不显示。
4. **分享链接是 bearer token。** 转发即公开，这是既有设计。点云入口要重申一次，不能让用户以为"进了点云才算公开"。
5. **二维投影会损失信息。** 两个人在平面上很近，未必真的相似。界面上应标明位置是近似，不给出精确距离。

## 八、路线

| 阶段 | 内容 | 新增的社交面 |
| --- | --- | --- |
| P0（已完成） | 结果、分享链接、好友、双人对比、只读后台 | 一对一的可见性 |
| P1 | 点云只读：匿名聚合、不可点开、自己高亮 | 一对多的"被看见" |
| P2 | 时间维度：最近 7 天新增的点、场的生长 | 在场感 |
| P3（可选） | 极轻的表达，例如给自己的点写一句状态 | 需要重新评估审核成本 |

明确不做：信息流、私信、关注关系、推荐排序。

## 九、可以直接说的话

> 我们不做社交网络。社交网络要你生产内容，我们要你只是存在。
>
> 每个人做完测试，会成为一片星图上的一个点。你能看见自己在哪，也能感觉到别人在附近，但你看不清他们是谁。
>
> 这不是一个广场，是一片夜空。

## 十、判断它是否成立的信号

不看注册数，看这三件：

1. 有人主动把画像设为可见（opt-in 率）
2. 有人第二次回来看自己的位置（回访）
3. 有人把点云截图发给朋友（自传播）

如果三者都没有，说明"看见位置"这件事不足以构成社区，应该回到 L1，把双人对比做深，而不是加功能。

## P1 实现记录

### 点从哪来：两个来源

第一版只让「展示中的画像」上图，上线当天就看出这个口径太小：123 人做完测试，只有 19 份画像上过云、14 个人选了展示。**星图只有 14 个点，而「仅我可见」挡掉的是 0 个人**——限制星图的不是隐私规则，是漏斗：「做完测试」这个动作本身不留任何痕迹。

所以现在有两个来源，都不带身份：

| 来源 | 条件 | 能否撤下 |
| --- | --- | --- |
| 展示中的画像 | `accounts.portrait_id` + `friends_visible = 1` | 能：改「仅我可见」、删云端记录、注销身份 |
| 一次测试完成 | 完成即写一行 `field_points`，无需注册 | 只能在同一台设备上撤（本机保存的 id 是唯一凭据） |

第二个来源的取舍要写清楚：

- **为什么值得**：社区想让人看见自己在人群里的位置，参照系就该是「所有做完的人」，而不是「愿意展示画像的人」。后者是一个自选样本，前者才是分布。
- **代价**：匿名点没有身份可查，所以**换了浏览器或清了本机数据就再也找不到它**。界面上必须这么讲，不能假装它可撤销。
- **去重**：一台设备一个点；已经有展示画像的人不再留匿名点（否则同一个人在图上出现两次）。设备之间无法去重——没有身份就没有办法判断「这两个点是同一个人」。
- **历史补不回来**：`metrics_daily` 只有计数器，那 123 份作答的向量从来没有存过。这条规则只对上线之后的完成有效。

### 「好友可见」的含义被扩大了

展示画像上图，意味着「好友可见」同时代表「星图上一个没有名字的点」。这一点写在权限管理的可见性说明里（`Settings.jsx`），否则就是静默扩大范围。第九节「分享即 opt-in」在这里要读成：**展示即 opt-in**。

### 为什么放弃「只返回密度」

构想里写的是「别人的位置只能感知密度」。实测过这条路：14×14 网格 + 每格至少 5 人才显示（k=5），N=50 时没有一个格子存活，N=100 只剩 1 个，N=300 才有 86/300 个点可见。它要等到一百人以上才有画面，而我们现在的规模是一片空白。

所以接口返回的是**匿名后的个体坐标**：只有 `[x, y]`，不带 id、昵称、原型、时间，也不保证顺序。坐标本身不指向任何人，配合「不可点开、无标签」，「看不清是谁」仍然成立。

### 投影：固定基底，离线算一次

`node scripts/compute-projection.js --apply` 用固定种子采样 20000 份随机作答，做 PCA：

| | 方差占比 | 主要载荷 |
| --- | --- | --- |
| PC1 | 40.1% | 处理深度 +0.51、表达 −0.48、社交能量 −0.47、感官敏感 +0.44 |
| PC2 | 29.9% | 变化亲和 +0.58、认知宽度 +0.55、模糊耐受 +0.39、边界清晰 −0.36 |

两维合计 **69.9%**，所以轴有可解释的名字：x = 向内 ↔ 向外，y = 安定 ↔ 流动。系数写进 `shared/projection.js`，前后端共用；位置不会随请求漂移，也不会因为某次重算而整张图翻面（脚本按 `expressivity` / `changeAffinity` 的载荷固定了符号）。

### 渲染：稀疏和密集都要好看

星图在 1 个点和 1500 个点下都必须站得住，否则它会随规模时好时坏。做法借 SpaceEngine，但把「光」换成「墨」：

它在黑底上做三件事：小于一个像素的东西并进背景亮度（LOD）、星体是带衰减的光斑而不是圆点、密集处几十个光斑叠成一片连续的光。所以放大不是把点变大，而是让更多东西被分辨出来；点多也不会变成一排排小点。

我们的底色是暖白纸，加法混合只会迅速糊成白色。所以反过来：**重叠等于积墨**。四层，从下到上：

1. **纸面** —— 一层很淡的径向渐变，只负责让尘埃有「底」。它一旦调重，整片对比度就被奶白吃掉。
2. **墨雾** —— 1/6 分辨率的累积层，放大回来就是一层软水彩。点在低分辨率上画 3.2px 半径的团，相邻的团会连成一片（画 1.7px 只是「同一批点变模糊」，不会成雾）。点少时不画，免得几个点也糊成脏斑。
3. **颗粒** —— 每个点一个软光斑 + 1.25px 的实心核。**没有实心核，稀疏的几个点只是纸上的脏斑，读不出「一颗」**。点少时更大更亮，点多时退成纹理。
4. **自己** —— 唯一的实心标记，永远是画面里最清楚的东西。

所有这些切换只读一个数 `density = (N - 6) / 140`，没有第二套逻辑：

| | 稀疏 | 密集 |
| --- | --- | --- |
| 颗粒透明度 | 0.58 | 0.18 |
| 颗粒尺寸 | ×1.45 | ×1 |
| 光晕 | N ≤ 12 时每颗一圈 | 不画 |
| 墨雾 | 不画 | 0.42 |
| LOD | 全画 | N > 500 隔 2 个画一个，N > 1200 隔 3 个 |

最后一行的依据：颗粒超过这个密度就开始变成噪点，SpaceEngine 的做法是把它们让给背景亮度，我们让给墨雾。

### 接口



- `GET /api/community/field` — 匿名可读。`{ version, total, completed, points: [[x,y]], you }`。带凭证时 `you = { x, y, archetype }`；带 `?point=<本机 id>` 时那个匿名点从 `points` 里摘出来作为 `you` 返回，客户端才知道该在哪画「你」。`completed` 是 `test_completed` 的聚合计数，用来说明「为什么图上是这个数」。
- `POST /api/community/point` — `{ id, vector }`，坐标由**服务端**投影，前端不决定位置。`id` 客户端生成，主键冲突即幂等。上限 20000 行，满了返回 429。
- `DELETE /api/community/point/:id` — 撤下。id 从不出现在任何响应里，能出示它就是创建它的人；重复撤下也返回成功。
- 展示画像那条完全由已有的 `portrait_id` + `friends_visible` 决定，不需要额外的下线接口。

### 空场

不造假数据，也不画原型星座做底图。场里没有点的时候，只在中间写两行字：「这里还是空的 / 第一个点，可以是你」。人少是早期，不是故障。

### 已知边界

- 二维只保留七成方差，靠得近不等于真的像。界面上标了「位置是近似的」，不提供精确距离。
- 小样本下，朋友之间本来就知道彼此的结果，理论上能猜到大概区域。所以不显示身份、不可点开、不显示顺序——能做的只有这些，界面必须把这一点说清楚。
- 匿名点是**公开写入**：任何人可以直接 POST 一个坐标。没有身份就没有限流依据，只能靠数量上限和「乱造点对谁都没好处」这一点兜着。真要收紧，得先引入一个不需要身份的频率闸门。
- 不显示「附近有多少人」这类读数：它天然是排名，不做。
