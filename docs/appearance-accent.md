# 主色与外观

## 问题

个人空间里的颜色不是设置项，是计算结果。

`PortraitMark` / `PortraitField` 的 `--ink` 直接取 `recordArchetype(record).color`，而这个 `color` 写死在 `src/data/archetypeProfiles.js` 里，10 个原型 10 个固定 RGB。头像也不是图片，就是这团颜色加三个模糊圆。所以「头像和主题没法控制」不是少一个开关，而是**颜色只有一个来源，且这个来源由测试结果决定**。

用户能换的只有「展示哪一份画像」，而每份画像的颜色又由原型决定。想要别的颜色，只能希望自己测出别的原型。

## 实测：这套颜色现在分不出来

拿雾、潮汐、底片三个人格做像素级合成（59×59 画布，三个圆按 `Personal.css` 的坐标、透明度与 7px 模糊叠在 `#f5f3f0` 上，取平均色），再算 CIE Lab 色差：

| 对比 | 原型色 ΔE | 头像合成后 ΔE |
| --- | --- | --- |
| 雾 ↔ 底片 | 6.05 | **1.85** |
| 潮汐 ↔ 底片 | 14.80 | 4.51 |
| 雾 ↔ 潮汐 | 11.24 | 3.43 |

人眼可辨阈值约 ΔE 2.3。第一对低于阈值，也就是「算出来的颜色不同，看起来是同一个」。10 个原型色两两平均 ΔE 只有 19.5，最大 43（暖流 ↔ 晶体），而合成过程会把差异压到约三分之一。

差异被抹平三次：

1. **好友列表根本没传颜色。** `Friends.jsx` 的「已经是好友」列表写的是 `<PortraitMark />`，没有 `color`，所有人走默认 `[180,185,195]`。这不是「看起来一样」，是字面上同一份颜色。
2. **头像里有 2/3 的色团是写死的。** `.pp-mark` 三个圆，只有第一个用 `rgba(var(--ink),.7)`；另外两个固定为暖沙 `196,165,137` 和天青 `143,181,196`。人格色只影响其中一个圆。
3. **原型色本身在同一色域。** 全部低饱和高明度，最大通道差 50，多数在 15 以内；再经 0.5 左右的透明度和 7px 模糊，差距被继续压缩。

这三条决定了后面两件事：色板不能沿用这 10 个颜色，头像也必须改成「三团同色系」。

## 结论

加一层**个人主色（accent）**：默认「跟随画像」，可以从一个**有限色板**里另选一个。

不做自由取色，不做头像上传，不做整页主题。理由是这三件事都会把「颜色」从一个受控的设计参数变成不可控的用户输入，而颜色在这个产品里同时承担了识别和氛围两个职责。

- 语义：未选择 = `follow`，跟随当前展示画像的原型色；选择了就固定成那个颜色。
- 未注册用户只写本机；注册用户走 `POST /api/account`，跟着身份跨设备同步。
- 好友列表/好友空间看到的是对方的主色；对方没选时用其展示画像的原型色（`palette` 字段，仅在画像对你好友可见时下发）。

## 明确不做

| 不做 | 原因 |
| --- | --- |
| 自由取色器 / 十六进制输入 | 用户会选出荧光绿、纯黑、高饱和红。这套配色全部是低饱和高明度，一个失控值就能把整页质感毁掉，且无法做对比度兜底 |
| 头像上传 | UGC 边界（审核、存储、内容安全），且会打破「头像即光场」的一致语言 |
| 整页背景换色 / 深色模式 | `#f5f3f0` 的纸感是基底，深色会把编辑感打散。最多做三档纸色，另立需求 |
| 记录级配色 | 每份记录一个颜色会让空间失去连续性，也会让历史记录变成调色盘 |

## 两层模型

这是整个方案的核心。现在颜色只有一个语义（「你是雾，所以你是灰蓝」），要让它可调，必须先把它拆成两层。

| 层 | 含义 | 谁决定 | 出现在 |
| --- | --- | --- | --- |
| 信息层 | 原型色 | 系统 | 过去的记录小圆点、完整画像页、分享页、好友对比 |
| 表达层 | 我的主色 | 用户 | 头像 `PortraitMark`、空间光场 `PortraitField`、空间强调色 |

不拆的直接后果：用户在空间里换一次主色，所有历史小圆点跟着变色，「那次是雾」这个信息就消失了。拆开之后，**历史记录永远显示当时的原型色，只有「现在的你」这一层可调**。

这条也解释了为什么主色是账号级而不是记录级：它描述的是「我怎么呈现自己」，不是「那次测试的结果」。

## 色板

不能沿用原型色。上一节的实测说明这 10 个颜色彼此太近，做成色板等于让用户在一排几乎一样的圆点里挑，选完头像也看不出变化。

色板必须满足**感知跨度**：任意两色在色板上的 ΔE ≥ 14，这样头像合成后仍有 ΔE ≥ 9，稳妥高于 2.3 的可辨阈值。在这个约束下把跨度拉开，同时把饱和度压在 25–40%，保住「纸感、低饱和」的品牌调性。

| key | 名称 | RGB | Hex |
| --- | --- | --- | --- |
| `follow` | 跟随画像 | — | 默认，取原型色 |
| `mist` | 雾面 | 178, 184, 196 | `#B2B8C4` |
| `sand` | 暖沙 | 203, 181, 146 | `#CBB592` |
| `clay` | 陶土 | 196, 143, 119 | `#C48F77` |
| `sky` | 晴空 | 139, 180, 212 | `#8BB4D4` |
| `deep` | 深海 | 98, 120, 152 | `#627898` |
| `lilac` | 丁香 | 176, 148, 188 | `#B094BC` |
| `lake` | 湖水 | 96, 142, 136 | `#608E88` |
| `charcoal` | 炭灰 | 108, 108, 114 | `#6C6C72` |

校验结果：最接近的一对是雾面 ↔ 晴空，ΔE 15.5；中位 29.1，最大 47.8。这组数值已写进单测，改色时自动拦住回归。

候选从 12 个收到 8 个：8 个刚好在 398px 的弹窗里排成一行，且色相覆盖中性、暖、橙、浅蓝、深蓝、紫、青绿、深灰，够用且不用翻页。再加回灰玫（ΔE 17.5）或苔绿（18.7）也仍在阈值内，但那一行就排不下了。

命名刻意用**色彩意象**而不是原型名：色板里如果出现「暖流」，用户会以为自己在选人格。名称只描述颜色本身。

### 硬约束：主色只作用于非文本元素

色板里最深的炭灰明度也只有 43%，最浅的雾面 76%，做文字颜色必然不达对比度。因此主色只能用在头像、光场、圆点、轨道线、分隔强调这类**形状与填充**上。文字仍然用 `--text` / `--muted`。现有 `.pp-tabs button[aria-current] i` 的 `#857596` 底边属于可换的范围（它是装饰条，不是文字）。

## 数据契约

### 本地

`localStorage` 的 `blur.account.v1` 直接多一个 `accent` 字段（`'follow'` 或色板 key），通过已有的 `updateAccountInfo({ accent })` 写入。未注册用户到此为止，不需要任何后端改动。

### 云端

```sql
-- migrations/0010_accent.sql
-- Additive and nullable: old workers ignore the column and never write it,
-- so this can ship before the code that reads it.
ALTER TABLE accounts ADD COLUMN accent TEXT;
```

不加 `CHECK` 约束：色板会演进，把枚举写进 DDL 意味着每次加色都要一次迁移。白名单在服务端校验，非法值一律存 `NULL`（等价于 `follow`）。

需要同步修改的写入点：

| 位置 | 改动 |
| --- | --- |
| `server/people.js` `account()` | 返回值加 `accent: row.accent \|\| null` |
| `server/people.js` `POST /api/account` | 接受可选 `accent`，不在白名单内则 `400`；写 `UPDATE accounts SET accent = ?` |
| `server/people.js` `DELETE /api/account` | 墓碑语句一并 `accent = NULL`，与清空昵称、简介保持一致 |
| `server/ghosts.js` 休眠墓碑化 | 同上，一并清空 |
| `server/people.js` `person()` | 载荷加 `accent` |

`person(row)` 目前被三处复用（`/api/people/by-code/:code`、`/api/friends` 列表、好友申请），而 `/api/friends/:publicId/profile` 是**内联构造 person**、不走 `person()`。四处都要在 SELECT 里补 `accent`，漏一处就会表现为「好友列表里有颜色、点头像进去又变回原型色」。

### 解析与降级

```js
// src/data/accents.js
export const ACCENTS = [/* key, name, rgb */];
export const ACCENT_KEYS = ACCENTS.map((a) => a.key);

// account.accent 优先；非法、缺失、老数据 → 原型色；连原型都没有 → 默认灰
export function resolveAccent(account, profile) {
  const picked = ACCENTS.find((a) => a.key === account?.accent);
  return picked?.rgb || profile?.color || [180, 185, 195];
}
```

调用方只有四处：`My.jsx`（头像与光场）、`FriendProfile.jsx`（对方的 `person.accent`）、`SharedProfile.jsx`（如渲染主色）、以及预览态。解析函数保持纯函数，不读 localStorage，方便单测。

服务端白名单从 `src/data/accents.js` 导入——`shared/profile.js` 已经有 `shared → src/data` 的引用先例（`DIMENSION_KEYS`），不新增反向依赖。

## 交互

入口在**编辑资料弹窗**里，不在设置。名字、简介、主色是同一件事——你希望别人怎么看到你——所以一次「保存资料」把它们一起提交。

最初的判断是把主色放进设置，理由是「主色是视觉偏好，和文字混在一起会让保存的语义含糊」。这个判断是错的：主色不是设备偏好，而是对外呈现的一部分，和昵称同级；放在设置里反而要求用户先想到「去设置里找颜色」。

弹窗内的结构：

1. 一个 44px 的头像 + 「主色 · 陶土」的当前值，选中即变，不写盘。
2. 「跟随画像」是一整行，不是色板里的一格：它描述的是一个模式（跟着画像变），不是一个颜色。行内说明会带上当前画像名，例如「用『雾』的原型色，换画像时一起变」。
3. 下面是 8 个 30px 圆点，桌面一行排开，窄屏折成 4×2。选中态用 2px 弹窗底色描边 + 外圈色环，和头像的视觉语言一致。
4. 保存走弹窗底部已有的「保存资料」：先写名字与简介，主色改过才再发一个 `POST /api/account`。没改主色就只有一个请求。

弹窗宽 466px、内容宽 398px，6 列刚好放下；高度约 590px，仍在 `max-height: min(84svh, 760px)` 之内，超出时内层滚动。

## 样式改造

`--ink` 的传递链本身不用改：`PortraitMark` 和 `PortraitField` 已经接收 `color` 数组并写成 `--ink`，只是调用方从传 `profile.color` 改成传 `resolveAccent(...)`。

真正要改的是 `.pp-mark` 的三个圆。现在第一个用 `rgba(var(--ink),.7)`，另外两个**硬编码**暖沙 `rgba(196,165,137,.48)` 和天青 `rgba(143,181,196,.5)`。人格色只占三个色团里的一个，另两个恒定贡献暖与冷，所以任何主色进去都会被拉回同一个中间调。

改法：三个圆全部由主色推导，取消固定色。

| 色团 | 现状 | 改后 |
| --- | --- | --- |
| 第一团（左上，主色） | `rgba(var(--ink), .7)` | `rgba(var(--ink), .85)` |
| 第二团（右下，提亮） | 暖沙 `.48` | `rgba(var(--ink-light), .55)`，`ink-light = min(255, ink × 1.18 + 8)` |
| 第三团（左下，压暗） | 天青 `.5` | `rgba(var(--ink-dark), .5)`，`ink-dark = ink × 0.82` |

实测效果：雾 ↔ 底片的头像 ΔE 从 1.85 升到 3.43。提升有限，因为**头像只能放大色板的差异，不能创造差异**——底子还是那两个相近的原型色。所以「放宽色板跨度」才是主因，这一条只是把损失从 3 倍收回到 2 倍。

同时修好友列表：`Friends.jsx` 的两处 `<PortraitMark />` 和 `FriendFinder.jsx` 的一处都补上颜色。这是独立于主色功能的缺陷，即使不做主色也应该修——现在好友列表里所有人头像完全一致。

## 发布顺序

主色是**纯增量**字段，因此可以按项目既有的「迁移先行」节奏走：

1. `npx wrangler d1 migrations list blur --remote` 确认待应用项。
2. `npm run db:migrate:remote` 应用 `0010_accent.sql`。老代码不读这一列，加列对现有账号、画像、好友、分享无影响。
3. 部署服务端（Pages Functions）：`/api/account` 读写 `accent`、`person()` 四处补字段。
4. 部署前端。

中间态的行为是明确的：新客户端 + 老服务端 → 用户选了色，服务端忽略，下次同步回退成「跟随画像」，不会报错；老客户端 + 新服务端 → 忽略多出来的字段，显示原型色。

未注册用户（纯本机）不依赖以上任何一步。

## 验收

- 未注册用户换主色，刷新后保持；清空本机记录不影响主色。
- 注册用户换主色 → 另一台设备用恢复密钥登录，主色一致。
- 好友视角看到的头像颜色与本人一致；对方设为「仅我可见」时头像仍显示其主色（颜色不是画像内容）。
- **好友列表与好友搜索结果里，不同的人头像颜色不同**；无画像的人用中性色，而不是所有人同一个默认值。
- 任意主色下，`.pp-mark` 不出现脏色；8 色逐个过一遍。
- 色板任意两色 ΔE ≥ 14，头像合成后 ≥ 9（写成单测）。
- 历史记录列表的小圆点始终是当时的原型色，不随主色变化。
- 老数据（无 `accent`）显示原型色；非法 `accent` 被服务端拒绝且不落库。
- 墓碑账号与休眠清理后 `accent` 为空。

## 待定

1. **头像形态**：主色之外是否再给 3 种有限形态（雾团 / 单点 / 原型符号）。属于同一条产品线，但会让 `.pp-mark` 从「一处颜色」变成「一套组合」，建议主色落地并观察后再定。
2. **中性色是否保留**：雾面与炭灰会削弱「主色=情绪」的表达，但给了「不想有颜色」的人一条出路。倾向保留。
3. **是否允许主色出现在分享页**：公开分享目前不渲染头像，若以后加上，主色要不要跟随身份走，需要和隐私口径一起定。
4. **原型色要不要重排**：现在的 10 个原型色平均 ΔE 19.5，合成后多数落在 2–5，肉眼基本不可分。如果产品希望「颜色能暗示人格」，这套值本身需要重排；如果不希望，就应该彻底放弃「颜色=人格」的暗示，让原型色只作为历史记录里的弱标记。这是比主色更上游的决策，本方案不处理。
